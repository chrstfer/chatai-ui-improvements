#+TITLE: ADR 0008: Turn-Level Message Targeting, MessageContentContainer, and Multi-Level Fold State Cycling
#+DATE: 2026-09-04

:PROPERTIES:
:STATUS: Accepted
:END:

* Status
Accepted

* Context
In previous iterations (ADR 0001, ADR 0006), the extension focused on code blocks in isolation (~code-block~, ~.code-block~, ~InSituCodeBlock~). While effective for standalone snippets, this code-block-centric paradigm presented structural limitations:
1. *Isolated Code-Block Scope*: Targeting only ~code-block~ DOM nodes isolated snippet enhancements from the conversational context (turn headers, user queries, assistant disclaimers, message-level actions).
2. *Binary Toggle Semantics*: Render and fold controls were modeled as binary boolean flags (~isRendered: boolean~, ~allFolded: boolean~). In hierarchical outlines (such as Emacs Org-mode, Markdown trees, and nested message structures), binary toggling fails to support standard outline cycling semantics (~FOLDED~ -> ~CHILDREN~ -> ~SUBTREE~).
3. *Tight Preact Coupling to Code Blocks*: ~InSituCodeBlock~ was tightly bound to individual ~<pre><code>~ containers rather than orchestrating the complete conversation turn body.

* Decision
We transition the extension from code-block-centric injection to turn-level message targeting and multi-level outline cycling:

** 1. Turn-Level Message Architecture (~user-query~ & ~model-response~)
The DOM discovery engine (~DomObserver~) now targets complete conversation message turns:
- *Turn Roots*: ~model-response~ (AI replies) and ~user-query~ (user prompts).
- *~StructuredMessageContainer~*: The top-level Preact boundary wrapping a message turn. It orchestrates turn-level lifecycle, portal projection into host action headers, and coordination between the turn toolbar and content body.
- *Retirement of ~InSituCodeBlock~*: ~InSituCodeBlock~ is superseded by the turn-level architecture and retired.

** 2. ~MessageContentContainer~ & In-Place Document Replacement
Inside ~StructuredMessageContainer~, the message content body (e.g. ~structured-content-container > div.container > message-content~ or ~div.markdown-main-panel~) is managed by ~MessageContentContainer~:
- *Plain Text Segments*: Native paragraph elements (~<p>...</p>~) are preserved and participate in turn-level folding.
- *Embedded Code Blocks*: Code block containers (~response-element.no-md > code-block~):
  - *Custom Renderer Available (e.g. Org-Mode)*: When a custom renderer is registered for the detected language, the code-block container is replaced in-place with its ~DocumentView~ (e.g. ~OrgDocumentView~), hiding the raw host element while in rendered mode.
  - *No Custom Renderer*: Non-rendered code blocks remain native host elements, but receive folding mechanics and summary badges (~📦 [lang] (N lines) — Click to expand~).

** 3. Turn-Level Message Toolbar
Each message turn renders a persistent ~MessageToolbar~ projected via Preact portal into the host header or action container:
- *Persistent "Fold" Button*: Labeled simply ~Fold~. Remains in the toolbar regardless of whether message content is custom-rendered or raw text, advancing message-level outline cycling.
- *Render Mode Cycling*: Render controls cycle through available representations (~Rendered~ <-> ~Raw~) rather than acting as disjoint boolean toggles.

** 4. Multi-Level Outline Fold State Cycling
Binary fold toggles are replaced across all hierarchy levels by a universal 3-state cycling engine:
$$\text{State Transition: } \text{FOLDED} \longrightarrow \text{CHILDREN} \longrightarrow \text{SUBTREE} \longrightarrow \text{FOLDED}$$
- *Universal Fold States*:
  - ~FOLDED~: Subtree and direct child contents are hidden.
  - ~CHILDREN~: Direct child headings are exposed, but their bodies and sub-descendants remain collapsed.
  - ~SUBTREE~: All descendant headings, subheadings, and body content are fully visible.
- *Leaf Nodes*: Sections without child headings cycle between ~FOLDED~ and ~EXPANDED~ (~SUBTREE~).
- *Local Header & Fold Boundary Cycling*: Clicking on any section heading or fold boundary icon in ~OrgDocumentView~ / ~Section~ advances its local fold state following the 3-state cycle.
- *HUD Global Control*: The HUD button is updated from "Fold/Unfold All" to *"Cycle Folding"*, dispatching global outline cycling across all registered message turns in the conversation.

* Consequences
** Positive
- Complete architectural coherence: conversation turns are treated as unified documents with text, headings, and embedded rich blocks.
- Authentic Org-mode outline cycling matching Emacs Org behaviour (~TAB~ on headings, ~S-TAB~ globally).
- Clean separation between turn orchestration (~StructuredMessageContainer~), body rendering (~MessageContentContainer~), and document views (~OrgDocumentView~).
- Single Preact root per message turn, adhering strictly to the declarative Preact-first guidelines.

** Negative
- Managing both message-level and nested block-level portal targets requires robust DOM selector heuristics across host UI updates.
